A base measure's fixed filter can read a to-one relationship's field, for example `measure.count('id', { filters: [eq('response.isTest', false)] })` on a `comments` dataset with `belongsTo response`, or `measure.avg('score', { filters: [eq('project.scoreType', 'nps')] })`. Before, join planning looked only at the query's dimensions, filters, ordering and enforced constraints, so the filter compiled to a bare `response.is_test` column and the query failed. Now selecting the measure, directly or through a derived, window or shift measure, a metric, or an omitted `measures` list, plans the same guarded single-match `LEFT ANY JOIN` (scoped by the target's row scope) that a query-level `response.isTest` filter does. This applies on the query-builder path and in semantic backend plans. The filter must name one hop over a `belongsTo` or `hasOne` relationship and a column-backed dimension of its target. A query that selects a measure breaking these rules fails validation and names the measure. Contract publishing refuses the measure too, and so does `Dataset.metric()` over it. A tenant-less dataset that joins a tenant-scoped target this way needs runtime tenancy, as for any other join. A relationship measure (`<relationship>.<measure>`) whose own filter reads a further relationship is refused as a second hop.

The filter publishes as the qualified reference the contract grammar already accepts, so contracts are unchanged. A contract that doesn't use the feature keeps its bytes and hash, and a rehydrated catalog compiles the same SQL; the decision 0005 equality corpus now covers this. A semantic backend plan's derived-metric inputs now resolve their filter fields to columns, as base metric plans already did.
