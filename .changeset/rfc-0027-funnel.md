Event datasets and funnel operations (RFC 0027).

- `@hypequery/datasets`: `dataset(..., { events: { entity, event? } })` declares that rows are events, with the event timestamp at `timeKey`. The declaration is published in deployment contracts, rehydrated and generated by codegen, and it appears in catalogs. `createPortableSemanticRuntime(...).executeEventOperation` runs funnels as one ClickHouse statement over the dataset's scoped source, so tenancy, row policies, enforced constraints and `FINAL` apply as they do to dataset queries. `strict` order uses a tie-safe `windowFunnel` transform and `any` order an exact array search. Both are checked against a brute-force sequence search on generated events. `prepareEventOperation` and `eventOperationErrors` expose the same planner.
- `@hypequery/protocol`: deployment contracts 2 and 3 accept a dataset `events` declaration (`validateProtocolDatasetEvents`). Semantic invocation 1 accepts a `funnel` operation (`validateProtocolEventOperation`, `ProtocolFunnelOperation`). `ProtocolSemanticInvocation['operation']` is now `ProtocolSemanticInvocationOperation`, so code that reads an invocation's operation must handle the new kind. Invocation 2 refuses the new kind under the lowest-version rule.
- `@hypequery/deployment`: the semantic data plane runs funnels through a new, optional `executeEventOperation` slot. Without it they are refused with `unsupported-capability`, so a dataset-only executor never receives one. Event operations are checked against the contract and the caller's visibility: the dataset declares events, fields are groupable or filterable and visible, step conditions stay off the time field, there is exactly one bounded time range of at most 731 days, the filter budget holds, and the estimated rows fit the row budget.
- `@hypequery/protocol-conformance`: new `event-operations-v1` family, and new cases in `deployments-v2`, `deployments-v3` and `semantic-invocations-v1`/`v2`.
