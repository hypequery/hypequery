- Business context, as in TypeScript: `hypequery.datasets.define_business_context(summary=, industry=, business_model=, customers=, audience=, goals=, kpis=, glossary=, conventions=, caveats=)` declares reviewed guidance for agents (what the business does, KPI definitions, a glossary, reporting conventions and data caveats). It never changes what a query returns. Text is trimmed, empty lists are dropped, and an invalid document raises `ProtocolBusinessContextError` naming the path, e.g. `$.glossary[1].term` for a term defined twice.
- `ClientContractExecutor.create(..., business_context=)` (and `ApiExecutorFactory` / `HttpExecutorFactory`) serves it to agents as `@hypequery/mcp` does: `list_datasets` carries it (only the summary over 32 KiB), and `get_business_context` is listed last and returns it. Without context, or with an empty document, the tools are unchanged; the manifest hash never changes. `hypequery.agent` in-process tools pick it up from the executor. `hypequery.mcp.format_business_context()` renders it as Markdown for a system prompt, byte for byte what `formatBusinessContext` writes.
- `prepare_dataset_bundle` and `write_dataset_bundle` take `business_context=` and write `business-context.json` in a version 2 bundle, with the same identity the TypeScript CLI gives the same contract and context. Without context a bundle stays version 1, so its identity is unchanged.
- `hypequery.protocol` adds the business context v1 document (`validate_protocol_business_context`, `prepare_protocol_business_context` and its encode and hash functions, `is_empty_protocol_business_context`, `ProtocolBusinessContextLimits`) and accepts version 2 deployment bundle manifests, which require a `businessContext` entry. It passes the shared `business-context-v1` conformance fixtures.
