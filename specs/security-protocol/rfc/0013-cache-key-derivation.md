# RFC 0013: Cache key derivation

- Status: Accepted
- Created: 2026-07-31
- Accepted: 2026-08-21
- Version: cache key 1
- Owners: Hypequery maintainers

Acceptance freezes cache key version 1. Changing the namespace grammar,
validation order, domain strings, input ordering, MAC algorithm, truncation
lengths, or store-key format now requires a new cache-key version or scheme.

## Summary

Semantic query results are cached under a key that a shared store, its
operators, and its telemetry can all observe. This RFC separates the value that
*identifies* a query from the value that *addresses* it in a store.

The canonical preimage stays in memory. The store key is derived from it with a
keyed MAC under a per-project, per-environment secret, and is opaque.

## Motivation

The current TypeScript signature is deliberately readable, and documents itself
as such: keys are canonical JSON "so stores can inspect them and tests can
assert on them". In practice one key contains the physical source table, the
selected dimensions and measures, every filter operator **and value**, and the
resolved tenant predicate **and value**:

```json
{"v":1,"kind":"dataset","target":"orders","source":"prod.orders",
 "filters":[{"field":"email","operator":"eq","value":"ana@example.com"}],
 "tenant":{"key":"tenant_id","operator":"eq","value":"acme_corp"}}
```

That string becomes the Redis key. It therefore also becomes the thing that
appears in `KEYS`/`SCAN` output, slow-log entries, eviction and expiry logs,
cache-hit metric labels, admin consoles, and any crash dump of the store. A
component that never had permission to read customer rows can read customer
identifiers and filter criteria out of the key space.

Hashing alone does not fix this. An unkeyed `SHA-256` of the preimage is
offline-guessable: the schema is known, the value space for a tenant identifier
or an email is small enough to enumerate, and an attacker with key-space access
can confirm guesses at their leisure. Confidentiality here requires a secret,
so the derivation is an HMAC and not a digest.

## Terminology

- **Preimage:** the canonical bytes identifying a query, as defined by the
  containing query contract and encoded under RFC 0001.
- **Namespace:** the `(project, environment)` pair a cache entry belongs to.
- **Cache-key secret:** ≥32 bytes of cryptographically random data held by the
  runtime for one namespace.
- **Store key:** the opaque string handed to the cache store.

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are to be
interpreted as described by BCP 14.

## Layers

```text
semantic query
    ↓  containing query contract
canonical preimage            ← memory only, never leaves the process
    ↓  HMAC-SHA-256(cache-key secret)
store key                     ← opaque, safe for shared stores and telemetry
```

The preimage remains available in-process for equality checks, debugging under
an explicit privileged diagnostic permission, and tests. It MUST NOT be used as
a store key, and MUST NOT appear in logs, metric labels, trace attributes,
error messages, or store telemetry.

## Preimage

The preimage is the RFC 8785 canonical UTF-8 bytes of the query identity
structure defined by the containing contract. This RFC does not define which
fields participate; it defines only what happens to those bytes afterwards.

An implementation MUST reject a preimage larger than 1,048,576 bytes with
`HQ_CACHE_KEY_PREIMAGE_TOO_LARGE`, matching the RFC 0001 canonical limit.

## Cache-key secret

- MUST be at least 32 bytes.
- MUST be generated by a cryptographically secure random source.
- MUST be distinct per `(project, environment)`. Reusing one secret across
  environments makes staging keys and production keys collide, which is both a
  correctness bug and a disclosure channel.
- MUST NOT be derived from the project name, environment name, deployment
  digest, or any other value an attacker can guess.
- MUST NOT be included in a deployment bundle, a public contract, an SDK
  package, a browser payload, or a Studio export.
- In hosted operation the runtime holds the secret. The authoring SDK does not
  need it and SHOULD NOT be given it.

## Validation order

Checks MUST be applied in this order, and the first failure determines the
reported code:

1. `HQ_CACHE_KEY_SECRET_MISSING` — the secret is absent or empty.
2. `HQ_CACHE_KEY_SECRET_TOO_SHORT` — the secret is shorter than 32 bytes.
3. `HQ_CACHE_KEY_INVALID_NAMESPACE` — the namespace is not an RFC 0008
   deployment target.
4. `HQ_CACHE_KEY_INVALID_VERSION` — `keyVersion` is outside its integer range.
5. `HQ_CACHE_KEY_PREIMAGE_TOO_LARGE` — the preimage exceeds 1,048,576 bytes.

The order is normative because a request may violate multiple constraints.
Implementations MUST reject an oversized string preimage from a safe length
bound before allocating its UTF-8 encoding.

## Derivation

Two domain-separated derivations use the same secret. Domain separation
prevents a value derived for one purpose from being valid for the other.

```text
NAMESPACE_DOMAIN = "hypequery.cache.namespace.v1"
ENTRY_DOMAIN     = "hypequery.cache.entry.v1"
```

Inputs are joined with a single `0x00` byte. The namespace is exactly the RFC
0008 deployment target: each token begins with an ASCII letter or digit and may
then contain ASCII letters, digits, `.`, `_`, `:`, or `-`. That grammar excludes
`0x00`, so the concatenation is unambiguous while accepting deployed target
names such as `project-1`. An implementation MUST validate the namespace under
RFC 0008 before deriving and MUST fail with `HQ_CACHE_KEY_INVALID_NAMESPACE`
otherwise. Skipping validation would reintroduce the ambiguity the separator
is there to prevent.

### Namespace token

```text
nsInput = NAMESPACE_DOMAIN || 0x00 || project || 0x00 || environment
nsToken = base64url(HMAC-SHA-256(secret, nsInput)[0..15])      // 22 chars
```

The namespace token is a stable, opaque prefix. It exists so a store that
supports prefix operations can evict or migrate one namespace without being
told which project it belongs to. It is truncated to 16 bytes because it is a
grouping label rather than an authentication tag; it never authorises access.

### Entry key

```text
entryInput = ENTRY_DOMAIN || 0x00 || project || 0x00 || environment
                           || 0x00 || preimage
mac        = base64url(HMAC-SHA-256(secret, entryInput))        // 43 chars
```

The namespace participates in the entry MAC directly rather than only through
the prefix, so two namespaces cannot produce the same MAC even if a store
ignores prefixes.

The entry MAC MUST NOT be truncated.

## Store key format

```text
key = "hq1." || keyVersion || "." || nsToken || "." || mac
```

Example:

```text
hq1.1.9pQ2rN4tXbLm7wKfYc0dEg.qX7mR2vK9wLpN4tY8cB1dF6gH3jS5kM0nP2rT4vW6xZ
```

- `hq1` identifies this derivation scheme. A future scheme uses a different
  literal, so a store can hold both during a migration.
- `keyVersion` is a decimal integer from 1 through 2147483647 with no leading
  zeroes.
- The base64url alphabet excludes `.`, so the four fields parse unambiguously.
- Total length is bounded at 128 bytes, which fits every store this protocol
  targets.

The key is opaque. Nothing may be inferred from it, and no component may parse
it for routing, authorisation, or tenancy decisions.

## Rotation

`keyVersion` MUST increment whenever the secret for a namespace changes.

Rotation is a cache flush, not a migration: entries written under the previous
version are unreachable and expire naturally. That is the intended failure
mode. Serving an entry derived under a retired secret would defeat the rotation
that retired it.

An implementation encountering a key whose scheme or version it does not
recognise MUST treat the lookup as a miss. It MUST NOT attempt to reinterpret
the key, and MUST NOT fail the request — a rotation must never turn into an
outage.

## Prohibited behaviour

- Using the preimage, or any substring of it, as a store key.
- Emitting the preimage to logs, metric labels, trace attributes, error
  messages, or store telemetry.
- Deriving the key with an unkeyed digest, or with MD5 or SHA-1.
- Using a non-secret value — project name, deployment digest, tenant
  identifier — as the HMAC key.
- Sharing one secret across environments or projects.
- Truncating the entry MAC.
- Embedding a tenant identifier, filter value, or physical source name in the
  key, in any encoding.
- Comparing keys with a non-constant-time comparison where an attacker controls
  one side and a timing signal is observable.

## Stable failure codes

- `HQ_CACHE_KEY_SECRET_MISSING`
- `HQ_CACHE_KEY_SECRET_TOO_SHORT`
- `HQ_CACHE_KEY_INVALID_NAMESPACE`
- `HQ_CACHE_KEY_INVALID_VERSION`
- `HQ_CACHE_KEY_PREIMAGE_TOO_LARGE`

Errors MUST NOT include the secret, the preimage, or any part of either.

## Limits

| Limit | Value |
| --- | ---: |
| Minimum cache-key secret bytes | 32 |
| Maximum preimage bytes | 1,048,576 |
| Namespace token bytes before encoding | 16 |
| Entry MAC bytes before encoding | 32 |
| Maximum store key bytes | 128 |
| `keyVersion` range | 1 – 2147483647 |

## Security considerations

- The store key is a confidentiality boundary, not an integrity one. It stops a
  reader of the key space from learning what was queried. It does not stop a
  writer of the store from poisoning a value; that requires trusting the store
  or authenticating the entry, which is out of scope here.
- HMAC rather than a digest is the load-bearing choice. The preimage's
  structure is public and its high-entropy fields are few, so an unkeyed hash
  is a dictionary attack away from disclosing tenant identifiers.
- Truncating the namespace token is safe because a collision merely groups two
  namespaces under one prefix; entry keys stay distinct through the full MAC.
- An implementation that cannot obtain a secret MUST fail closed with
  `HQ_CACHE_KEY_SECRET_MISSING` rather than falling back to an unkeyed digest
  or to the readable preimage. A silent fallback would reproduce exactly the
  disclosure this RFC removes.
- Caching remains optional. A deployment without a configured secret runs
  without a result cache; it does not run with an insecure one.

## Compatibility

Changing the namespace grammar, validation order, a domain string, the MAC
algorithm, truncation lengths, key format, or input ordering requires a new
cache-key version or scheme. Package SemVer does not select this version.
