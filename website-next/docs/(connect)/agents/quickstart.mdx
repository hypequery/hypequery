This page gives the agent in your product tools over the `orders` dataset from [Model your data](/docs/quick-start).
The model calls `list_datasets`, `get_dataset_schema` and `query_dataset` instead of writing SQL, and every query is
scoped to the customer who is signed in.

`hypequeryTools({ executor })` runs those tools inside your own backend, against your own ClickHouse: no MCP server to
host, no token, and no network hop between your route and the tools. Use it wherever your app already holds the
ClickHouse connection and the user's session: a Next.js route handler, an Express or Hono server, or a job. To run
the tools as a separate service instead, connect over MCP: see [In your backend, or over MCP](#in-your-backend-or-over-mcp).

<Callout type="info" title="TypeScript only, for now">
  `@hypequery/agent` is a TypeScript package. From Python today, serve the dataset over MCP
  ([Connect via MCP](/docs/mcp/quickstart)) and connect your agent framework's MCP client to it: the OpenAI
  Agents SDK, Pydantic AI and LangChain all have one.
</Callout>

<CodeBlock>
```bash
npm install ai @hypequery/agent @hypequery/mcp
```
</CodeBlock>

It builds on the packages from Model your data (`@hypequery/datasets` and `@hypequery/clickhouse`).

## Create the tools for one request

`createMCPExecutor` from `@hypequery/mcp` is the engine behind the tools. Give it your datasets, your dataset client
(`analytics`) and a tenant, and it:

1. **Checks the setup** when you create it: a tenant-scoped dataset with no `tenantId` throws, so nothing runs
   unscoped.
2. **Builds the tools' input schemas** from your datasets, so the model can only name real datasets, dimensions,
   measures and filters.
3. **Runs each call**: it validates the arguments against the dataset, runs the query through your `analytics`
   client with the tenant filter added, and returns the rows, or an error with a hint the model can act on.

It's the same engine `hypequery mcp` serves to Claude and Cursor, which is where the name comes from. Here nothing
is served: `hypequeryTools({ executor })` calls it directly, in your route, with no MCP server and no network hop.

The executor is bound to one tenant, so create it per request, with the tenant from your server-side session:

<CodeBlock>
```ts
// app/api/chat/route.ts
import { hypequeryTools } from '@hypequery/agent/ai-sdk';
import { publishDatasets } from '@hypequery/datasets';
import { createMCPExecutor } from '@hypequery/mcp';
import { convertToModelMessages, streamText } from 'ai';
import { analytics } from '@/analytics/client';
import { Orders } from '@/analytics/datasets';

const datasets = publishDatasets().publish(Orders).build();

export async function POST(request: Request) {
  const session = await getSession(request); // your auth
  if (!session) return new Response('Sign in first.', { status: 401 });

  const executor = createMCPExecutor({ datasets, analytics, tenantId: session.tenantId });
  const tools = await hypequeryTools({ executor });

  const { messages } = await request.json();
  const result = streamText({ model, tools, messages: await convertToModelMessages(messages) });
  return result.toUIMessageStreamResponse();
}
```
</CodeBlock>

On the client, `useChat` from `@ai-sdk/react` renders the streamed answer and each tool call. The
[in-app analytics agent](/examples/in-app-analytics-agent) starter wires up both, with two demo customers.

The same `{ executor }` source works with every adapter:

<CodeBlock>
```ts
import { hypequeryTools as anthropicTools } from '@hypequery/agent/anthropic';
import { hypequeryTools as openaiTools } from '@hypequery/agent/openai-agents';

const hq = await anthropicTools({ executor });   // hq.tools for messages.create, hq.toolResults(...)
const agentTools = await openaiTools({ executor }); // tools for new Agent({ tools })
```
</CodeBlock>

## Tenant isolation

The tenant comes from the `tenantId` you pass to `createMCPExecutor`, which you take from your server-side session.
Never read it from the request body, a header the browser sets, or the model.

For a dataset with a `tenantKey`, the executor fails closed:

- `createMCPExecutor` throws if a tenant-scoped dataset is registered without a `tenantId`;
- every query gets `WHERE <tenantKey> = <tenantId>`, so grouping by the tenant field returns one row;
- a filter on the tenant field is refused with a non-retryable `MCP_INVALID_ARGUMENTS`, so the model does not retry;
- the tool input schemas have no tenant argument, so a `tenantId` the model invents is rejected.

The [in-app analytics agent](/examples/in-app-analytics-agent) starter tests this against ClickHouse with a model
scripted to try each of these.

## Choose which tools the agent gets

By default the agent gets every tool the executor lists, including `query_metric`. Pass `tools` to list only some;
the rest are neither listed nor callable:

<CodeBlock>
```ts
const tools = await hypequeryTools({
  executor,
  tools: ['list_datasets', 'get_dataset_schema', 'query_dataset', 'get_business_context'],
});
```
</CodeBlock>

`onResult` works as it does with an endpoint: it is called with each tool's result.

## Business context

Pass `businessContext` to the executor and the agent reads your KPI definitions, glossary, conventions and caveats
from `list_datasets` and `get_business_context`:

<CodeBlock>
```ts
const executor = createMCPExecutor({ datasets, analytics, tenantId: session.tenantId, businessContext });
```
</CodeBlock>

See [Business context](/docs/agents/business-context).

## In your backend, or over MCP

`hypequeryTools` takes its tools one of two ways. Both give the model the same tools, schemas and error envelope, so
you can switch later without changing your agent loop.

| | In your backend (`{ executor }`) | Over MCP (`{ url, token }`) |
|---|---|---|
| Use it when | The agent runs in the app that holds the ClickHouse connection and the user's session | The tools should live elsewhere: a shared service, or hypequery Cloud |
| Typical case | A Next.js or Express app with a chat feature | A separate agent service, several apps sharing one endpoint, or one endpoint for your in-app agent and for Claude and Cursor |
| Tenant from | `tenantId` from your session, in the same process | A per-user token the MCP server verifies |
| Extra infrastructure | None | An MCP server you run, or hypequery Cloud (coming soon) |
| Datasets live in | Your app's code | The MCP server's project, which can deploy on its own |

Start in your backend: it is the simplest, with no extra service and no tokens. Move to MCP when more than one app or
agent needs the same governed tools.

### Connect to your own MCP server

`hypequery mcp --http` serves your datasets at `http://127.0.0.1:3333/mcp` (see [Remote MCP](/docs/mcp/remote) for
TLS, hosts and OAuth). Point `hypequeryTools` at it with the caller's token:

<CodeBlock>
```ts
import { hypequeryTools } from '@hypequery/agent/ai-sdk';

const tools = await hypequeryTools({
  url: 'https://mcp.example.com/mcp', // http is allowed for localhost only
  token: () => getUserToken(session), // asked for before every request
});
```
</CodeBlock>

How the server authenticates decides the tenant:

- **A shared key** (`HYPEQUERY_MCP_KEY=… npx hypequery mcp --http --tenant acme`) gives every caller the same tenant.
  Fine for one team; not for a chat your customers use.
- **Your API's auth** (no `HYPEQUERY_MCP_KEY`) verifies each caller with the `auth` and `tenant` from `defineServe`,
  for example `createJwtStrategy` with the MCP URL as its audience. Each user's token then carries their own tenant,
  exactly as over REST. Use this for a multi-tenant chat.

### On hypequery Cloud (coming soon)

hypequery Cloud is not live yet. When it launches, it will host the same MCP endpoint against your ClickHouse, using a
read-only user, so your data stays where it is. Your server mints a short-lived end-user token per session with
`mintAgentToken`, and Cloud adds permission sets, release history for datasets and business context, and request
logs. See [Tools for your agent](/docs/agents/tools). The starter switches between your backend and Cloud with
`HYPEQUERY_MODE`.

### Why not the AI SDK's own MCP client?

The AI SDK can connect to any MCP server itself (`@ai-sdk/mcp`). `hypequeryTools` adds what hypequery's tools need:
errors the model can act on (code, hint, retryable), a token function that is called before every request so
short-lived tokens refresh, a request id on every result for explaining an answer later, and the same tool shape as
`{ executor }`, so you can switch between the two without changing your code.
