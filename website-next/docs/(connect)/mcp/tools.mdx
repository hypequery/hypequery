The MCP server exposes semantic tools over your dataset registry. Agents do not receive a SQL tool.

`list_datasets` and `get_dataset_schema` are always listed. `query_metric` is listed once a dataset defines a named metric, and `query_dataset` once a dataset can be queried directly; a query tool with nothing under it is left out, so an agent never spends a call on it.

Each query tool's input schema lists every dataset's dimensions, measures and filters in one object, which is the shape Claude, OpenAI and other model APIs accept. Each option is labelled with the datasets it belongs to (for example `For dataset "orders" only.`), but the schema cannot enforce that, so the server checks every call against that dataset's own fields and returns an `MCP_INVALID_ARGUMENTS` error the agent can correct from.

## `list_datasets`

Lists registered datasets with description, dimension count, measure count, and metric count. Each entry also has `queryable`, which is `false` when the dataset can only be reached through named metrics.

When bridging a Python backend (`--client-contract-url`), each `description` is the fixed text `Authorized client endpoints.`, and the counts cover every endpoint the principal may call for that dataset.

<CodeBlock>
```json
{
  "name": "list_datasets"
}
```
</CodeBlock>

Example response:

<CodeBlock>
```json
{
  "datasets": [
    {
      "name": "orders",
      "description": "Customer orders and revenue data",
      "dimensionCount": 5,
      "measureCount": 4,
      "metricCount": 2
    }
  ],
  "total": 1
}
```
</CodeBlock>

## `get_dataset_schema`

Returns metadata for one dataset, including dimensions, measures, named metrics, filters, tenant key, time key, limits, and relationship metadata when present.

When bridging a Python backend, the response is `{ name, queryable, endpoints: [...] }` instead. Each endpoint carries its own dimensions, measures, filters (with the operators each one allows), limits and time settings. Tenant keys, time-key columns and relationship metadata stay on the server. Relationship entries include `queryable` and `fields`, so agents can discover which related fields (for example `customer.country`) a query may reference. See [Relationships](/docs/datasets/relationships).

<CodeBlock>
```json
{
  "name": "get_dataset_schema",
  "arguments": {
    "dataset": "orders"
  }
}
```
</CodeBlock>

Labels and descriptions from your dataset definitions are included here, so they matter for agent behavior. Synonyms, example values, formats, units and currencies are included too: in local mode on each field, and when bridging a backend in each endpoint's `annotations.fields`.

## `query_metric`

Runs one named metric handle attached to a dataset. Listed only when at least one dataset defines a metric.

<CodeBlock>
```json
{
  "name": "query_metric",
  "arguments": {
    "dataset": "orders",
    "metric": "revenue",
    "dimensions": ["country"],
    "filters": [
      { "field": "status", "operator": "eq", "value": "completed" }
    ],
    "orderBy": [
      { "field": "revenue", "direction": "desc" }
    ],
    "limit": 10
  }
}
```
</CodeBlock>

Use `query_metric` when the agent should ask for a stable KPI such as `revenue`, `averageOrderValue`, or `monthlyRevenue`.

## `query_dataset`

Runs an ad hoc dataset query with selected dimensions and measures.

<CodeBlock>
```json
{
  "name": "query_dataset",
  "arguments": {
    "dataset": "orders",
    "dimensions": ["country", "status"],
    "measures": ["revenue", "orderCount"],
    "filters": [
      { "field": "status", "operator": "eq", "value": "completed" }
    ],
    "grain": "month",
    "limit": 100
  }
}
```
</CodeBlock>

The MCP argument is called `measures`, matching dataset queries in `@hypequery/datasets`. Derived or named metrics such as `averageOrderValue` are not measures and can only be queried through `query_metric`.

At least one dimension or measure must be specified, otherwise the query is rejected.

## Other query arguments

Besides `dimensions`, `measures`, `filters`, `orderBy`, `grain`, `limit` and `offset`, the query tools accept:

- `having`: conditions on aggregated measure values (`query_dataset`);
- `timezone`: an IANA zone for time buckets and offset-free timestamps;
- `orderBy` on `period` when `grain` sets a time grain.

Two arguments depend on how the server runs:

| | Local datasets (`hypequery mcp`) | Bridging a backend (`--client-contract-url`) |
| --- | --- | --- |
| `includeMeta` | Rejected | Returns `meta` with the request id, row count and pagination |
| `query_dataset` without `measures` | No measures: dimensions only | The endpoint's default measures |

## Analysis arguments

A server over datasets, local or hosted, also offers the analysis features of the semantic query protocol. Each one is in the tool's input schema only when the server can run it, so an agent never sees an option every call would fail.

| Argument | Tools | What it does |
| --- | --- | --- |
| `filters` groups | both | `{ "and": [...] }`, `{ "or": [...] }` and `{ "not": ... }` beside flat filters, nested freely. Each filter inside keeps its field's operators. |
| `inDateRange` | both | A relative range on a time field, resolved by the server in the query `timezone`. |
| `timeKey` | both | The time axis for `grain`, on a dataset with more than one. |
| `fill` | `query_dataset` | Every `grain` period of the filtered time range, empty ones included. |
| `calculations` | `query_dataset` | Query-scoped variants of measures: `filter`, `shift`, `window`, `formula`, `compare`, `rank` and `share`. |
| `limitBy` | `query_dataset` | The first `n` rows of each group, in `orderBy` order. |
| `other` | `query_dataset` | The top `n` values of a dimension, with the rest grouped under one label. |

The flat filter list still works and still means AND, so existing calls are unchanged.

<CodeBlock>
```json
{
  "name": "query_dataset",
  "arguments": {
    "dataset": "orders",
    "dimensions": ["country"],
    "measures": ["revenue", "orderCount"],
    "filters": [
      { "or": [
        { "field": "country", "operator": "eq", "value": "US" },
        { "field": "country", "operator": "eq", "value": "CA" }
      ] },
      { "not": { "field": "status", "operator": "eq", "value": "refunded" } },
      { "field": "createdAt", "operator": "inDateRange", "value": "last 3 months" }
    ],
    "grain": "month",
    "calculations": [
      { "name": "aov", "formula": { "op": "divide", "args": ["revenue", { "op": "nullIfZero", "args": ["orderCount"] }] } },
      { "name": "vs_prior", "compare": { "to": "previousPeriod", "measures": ["revenue"] } }
    ],
    "orderBy": [{ "field": "revenue_change_pct", "direction": "desc" }]
  }
}
```
</CodeBlock>

`inDateRange` takes `today`, `yesterday`, `this <unit>`, `last <unit>`, `last <N> <unit>s` and `month to date`, `quarter to date` or `year to date`, where the unit is `day`, `week`, `month`, `quarter` or `year`. `this` ranges include the whole current period; `last` ranges end where the current period starts, so `last 7 days` ends yesterday. A filter allows `inDateRange` when its field is a time axis and it allows both `gte` and `lt`.

`shift`, `window` and `compare` calculations, and `fill`, need `grain` and one bounded range on the time axis: a top-level `inDateRange`, `between`, or a lower and an upper bound. `compare` adds `<measure>_previous`, `<measure>_change` and `<measure>_change_pct` columns. `orderBy` and `having` can name any calculation output. A result with calculations carries `meta.calculations`, which types each output column and marks ratios with `format: "ratio"`.

A rule the schema can't express, such as a missing time range or a trailing window that doesn't fit the grain, comes back as `MCP_INVALID_ARGUMENTS` with the reason, so the agent can fix the call.

A server turns features off with `queryFeatures` on `createMCPExecutor` or `createMCPDiscoveryExecutor`. Every feature is on by default. A gateway whose data plane validates under expression extension 1 sets `calculations: false`, which removes `calculations`, `limitBy` and `other`:

<CodeBlock>
```typescript
createMCPDiscoveryExecutor({ datasets, queryFeatures: { calculations: false } });
```
</CodeBlock>

The other switches are `having`, `filterGroups`, `relativeDates`, `fill` and `timeKey`. Filter groups and formulas nest, so the schema describes them with `$ref`s to its root `definitions`. If a model API you target can't read `$ref`, set `filterGroups: false` and `calculations: false` for a schema without any.

When bridging a backend (`--client-contract-url`), none of these are offered: a client contract does not describe them yet. Sending one anyway is refused with `MCP_INVALID_ARGUMENTS`, never ignored.

## Pagination

`query_metric` and `query_dataset` both accept `limit` and `offset` for paging through large result sets. `offset` skips the given number of rows before returning results.

- `limit` defaults to 100. `offset` may not exceed 10,000.
- A dataset's own limits, and when bridging, each endpoint's `maxLimit`, can lower both caps.
- A Python backend clamps a `limit` above its endpoint maximum without failing. Send `includeMeta: true` and read `meta.pagination.limit` to see the limit that applied, and `hasMore` to know whether to page.

## Errors

A failed tool call returns `isError: true`, a text line such as `Error [MCP_INVALID_ARGUMENTS]: …`, and the same details as structured content:

<CodeBlock>
```json
{ "error": { "code": "MCP_INVALID_ARGUMENTS", "category": "correctable_input", "message": "…", "retryable": false, "correctable": true } }
```
</CodeBlock>

| Code | Category | Retry? | Meaning |
| --- | --- | --- | --- |
| `MCP_INVALID_ARGUMENTS` | `correctable_input` | fix the call | An argument is unknown, the wrong type, or outside a limit |
| `MCP_NOT_FOUND` | `correctable_input` | fix the call | The dataset or metric doesn't exist |
| `MCP_UNKNOWN_TOOL` | `correctable_input` | fix the call | The tool name is not one the server exposes |
| `MCP_UNAUTHORIZED` | `unauthorized` | no | The backend refused the credentials |
| `MCP_STALE_CONTRACT` | `stale_contract` | after a restart | Definitions changed since the bridge loaded them |
| `MCP_REQUEST_CANCELLED` | `budget` | no | The client cancelled the call |
| `MCP_QUERY_TIMEOUT` | `budget` | yes | The query exceeded its time budget |
| `MCP_RESULT_TOO_LARGE` | `budget` | no | The response exceeded its byte budget; narrow the query |
| `MCP_CATALOG_TOO_LARGE` | `budget` | no | Too many endpoints to list within the catalog budget |
| `MCP_RATE_LIMITED` | `budget` | yes, after `retryAfterSeconds` | A hosted server's rate limit or quota refused the call |
| `MCP_EXECUTION_FAILED` | `internal` | yes | The query or backend failed; details stay in server logs |

A hosted server may add these optional fields:

| Field | Meaning |
| --- | --- |
| `retryAfterSeconds` | How long to wait before retrying |
| `relist` | Call `list_datasets` and the schema tools again before retrying |
| `reason` | The host's own stable code for the failure, such as `HQ_SEMANTIC_TENANT_REQUIRED`; `code` stays the portable classification |
| `hint` | The next action, in one sentence |
| `docsUrl` | A page that explains the failure and how to fix it |
| `requestId` | The host's request id, to find the call in its logs |

A host that executes through the semantic data plane builds these with `mcpToolErrorFromSemanticFailure` and returns them with `createMCPErrorResponse`.

## Prompt

The server also exposes a `dataset_guide` prompt that helps an MCP client explain how to query the registered datasets.

## Operators and grains

Filter operators, as limited by each field's type:

| Field type | Operators |
| --- | --- |
| string, timestamp | all of the operators below |
| number | all except `like` |
| boolean | `eq`, `neq`, `in`, `notIn` |

A dataset's named filter can declare a narrower list, which `get_dataset_schema` reports per filter. `in` and `notIn` take a non-empty list, and `between` takes two values. `isNull` and `isNotNull` take no value, and are allowed only where a filter lists them. `inDateRange` is described under [Analysis arguments](#analysis-arguments).

- `eq`
- `neq`
- `gt`
- `gte`
- `lt`
- `lte`
- `in`
- `notIn`
- `between`
- `like`

Supported time grains, narrowed per dataset by its catalog `supportedGrains`:

- `minute`
- `hour`
- `day`
- `week`
- `month`
- `quarter`
- `year`
