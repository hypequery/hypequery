Filters are structured query objects. They are used by dataset queries and filtered measures.

<CodeBlock>
```typescript
import {
  between,
  eq,
  gt,
  gte,
  inList,
  isNotNull,
  isNull,
  like,
  lt,
  lte,
  neq,
  notInList,
} from '@hypequery/datasets';
```
</CodeBlock>

## Filter helpers

<CodeBlock>
```typescript
eq('status', 'completed')
neq('status', 'cancelled')
gt('amount', 100)
gte('amount', 100)
lt('amount', 1000)
lte('amount', 1000)
inList('country', ['US', 'UK', 'CA'])
notInList('status', ['cancelled', 'refunded'])
between('createdAt', '2026-01-01', '2026-01-31')
like('email', '%@example.com')
isNull('churnedAt')
isNotNull('churnedAt')
```
</CodeBlock>

Each helper returns a filter with a field, operator, and value. `isNull` and `isNotNull` take no value: they render `IS NULL` and `IS NOT NULL`, and a filter that sets `value` on them is rejected.

<CodeBlock>
```typescript
eq('status', 'completed')
// { field: 'status', operator: 'eq', value: 'completed' }
```
</CodeBlock>

## Timestamp values

Timestamp filters take ISO 8601 strings. A date (`'2026-02-01'`) or an
offset-free date-time (`'2026-02-01T00:00:00'`, `'2026-02-01 00:00:00'`) is
read as local time in the query timezone. A value carrying `Z` or an offset,
such as `new Date().toISOString()` produces, is an instant and selects the
same rows in every query timezone:

<CodeBlock>
```typescript
gte('createdAt', '2026-02-01T00:00:00Z')      // instant
gte('createdAt', '2026-02-01T00:00:00.000Z')  // instant, fractional seconds kept
gte('createdAt', '2026-02-01')                // local midnight in the query timezone
```
</CodeBlock>

A `between` or `notIn` may mix the two forms; each bound keeps its own
meaning. An `in` list must use one form or the other.

## Use filters in dataset queries

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  dimensions: ['country', 'status'],
  measures: ['revenue', 'orderCount'],
  filters: [
    eq('status', 'completed'),
    between('createdAt', '2026-01-01', '2026-01-31'),
  ],
});
```
</CodeBlock>

## Relative date ranges

`inDateRange` filters a time axis by a range relative to today:

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  measures: ['revenue'],
  filters: [{ field: 'createdAt', operator: 'inDateRange', value: 'last 30 days' }],
});
```
</CodeBlock>

| Value | Range |
| --- | --- |
| `today`, `yesterday` | That day |
| `this week`, `this month`, `this quarter`, `this year` | The whole current period, including the days still to come |
| `last week`, `last month`, `last quarter`, `last year` | The previous whole period |
| `last 7 days`, `last 3 months`, … (`last N <unit>s`, N from 1 to 9999) | N whole periods that end where the current one starts. The current period isn't included, so `last 7 days` ends yesterday |
| `month to date`, `quarter to date`, `year to date` | From the start of the current period through today |

The client works out the range once per query, in the query timezone, as `>= start` and `< end` dates. A cached result therefore never answers for a different day. Weeks start on Sunday, like the `week` grain. `inDateRange` works only on a time axis (`timeKey` or one of `timeKeys`), and the filter must allow `gte` and `lt`. Measure filters and segments can't use it. Pass `now` to `createDatasetClient` to pin the clock in tests.

## Combine filters with `and`, `or` and `not`

A query's `filters` list is ANDed. Nest `{ or: [...] }`, `{ and: [...] }` and `{ not: filter }` groups in it for anything else:

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  measures: ['revenue'],
  filters: [
    { or: [eq('country', 'US'), eq('country', 'CA')] },
    { not: eq('status', 'refunded') },
  ],
});
```
</CodeBlock>

Each comparison in a group is validated like a top-level one, and `maxFilters` counts comparisons, not groups. Under `not`, the negated operator is what must be allowed: `not eq` needs `neq`, `not between` needs `lt` and `gt`, and `not like` needs `like`. Tenant filters, enforced constraints and segments stay outside any `or` you write. Window, shift and filled queries need their time range as top-level filters. Groups need the `queryBuilder` path and a builder with `whereGroup`, `orWhere` and `orWhereGroup`, which `@hypequery/clickhouse` provides.

## Filter aggregated values with `having`

`filters` narrow the rows before they are aggregated. To keep only the groups whose aggregated value passes a condition, such as countries with more than 10,000 in revenue, use `having`:

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  dimensions: ['country'],
  measures: ['revenue', 'orderCount'],
  filters: [eq('status', 'completed')],
  having: [
    { measure: 'revenue', operator: 'gt', value: 10_000 },
    { measure: 'orderCount', operator: 'between', value: [2, 50] },
  ],
});
```
</CodeBlock>

- Each condition must name a measure the query selects, including derived measures. A condition on an unselected measure is rejected.
- Values are finite numbers, bound as query parameters. Operators are `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `between` (a `[min, max]` pair), `in` and `notIn` (non-empty arrays).
- Conditions apply after grouping and before ordering and limits. A group whose measure is `NULL` never matches.
- A dataset's `limits.maxFilters` bounds `filters` and `having` together.
- Queries that select window or shift measures do not accept `having`.

## Use filters in measures

Filtered measures are useful when a business state should always be part of the aggregation.

<CodeBlock>
```typescript
import { dataset, dimension, eq, measure } from '@hypequery/datasets';

const Orders = dataset('orders', {
  source: 'orders',
  dimensions: {
    status: dimension.string(),
  },
  measures: {
    completedRevenue: measure.sum('amount', {
      filters: [eq('status', 'completed')],
    }),
    refundedRevenue: measure.sum('amount', {
      filters: [eq('status', 'refunded')],
    }),
  },
});
```
</CodeBlock>

## Restrict filter operators

By default, filterable dimensions become available as filters. Use the dataset `filters` map when you want a named filter contract or a restricted operator set.

<CodeBlock>
```typescript
import { dataset, dimension, measure } from '@hypequery/datasets';

const Orders = dataset('orders', {
  source: 'orders',
  dimensions: {
    status: dimension.string(),
    country: dimension.string(),
  },
  measures: {
    revenue: measure.sum('amount'),
  },
  filters: {
    status: {
      __type: 'filter_definition',
      field: 'status',
      operators: ['eq', 'neq', 'in', 'notIn'],
    },
  },
});
```
</CodeBlock>

With this contract, `status` allows only the listed operators, and `country` is still filterable with the default operators. Declared filters add to the dimensions marked `filterable`; they do not replace them. TypeScript checks these names and operators in dataset and metric execution, Serve API inputs, and React hooks, including infinite-query hooks. The filter helpers preserve their operator literals, so `eq('status', 'completed')` works with an `eq`-only policy.

Use `DatasetQueryFor<typeof Orders>` or `MetricQueryFor<typeof Orders, 'revenue'>` when storing query inputs in variables. `DatasetFilterNames<typeof Orders>` describes the exposed names, and `DatasetFilterFor<typeof Orders>` describes the field/operator pairs. A declared filter's name is its key in `filters`, which may differ from its backing dimension. A dimension named directly takes the operators of the filters declared on it, so declaring `planFilter` on `plan` with `operators: ['eq']` also limits `plan` to `eq`.

`isNull` and `isNotNull` are opt-in for query filters: a filter allows them only when its `operators` list names them, as in `operators: ['gte', 'isNull', 'isNotNull']`. Measure filters and segments can use them without a list.

Every dimension with `filterable !== false` is filterable, whether or not `filters` is declared; set `filterable: false` to remove one, or declare a filter to expose a `filterable: false` dimension under its own policy. One-hop `belongsTo` and `hasOne` filters reach the target's filterable dimensions and the filters it declares under a dimension's name, with the target's operator policy. SQL-backed target dimensions, `hasMany`, and multi-hop paths remain unavailable.

Keep dataset definitions inferred to retain their literal policies. Broad `DatasetInstance` or `SemanticFiltersDefinition` annotations lose that information. Explicit result-row generic calls retain the legacy dynamic-query contract. Filter values and runtime tenant restrictions continue to be validated when the query runs.

## Order helpers

`asc` and `desc` create structured order clauses.

<CodeBlock>
```typescript
import { asc, desc } from '@hypequery/datasets';

await analytics.execute(Orders, {
  dimensions: ['country'],
  measures: ['revenue'],
  orderBy: [desc('revenue'), asc('country')],
});
```
</CodeBlock>

## Tenant filters

When runtime tenancy is active, explicit filters on the tenant field are rejected. Use runtime tenant context instead.

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  measures: ['revenue'],
  filters: [eq('tenantId', 'tenant_123')],
}, {
  runtime: {
    tenant: 'tenant_123',
  },
});
// Error: Cannot filter on tenant field "tenantId" when runtime tenancy enforcement is active.
```
</CodeBlock>
