The chat embed puts hypequery's assistant inside your app, for each of your users. They ask in plain words, and the
assistant answers by running queries as that user. It sees only their customer's rows, within the permission set you
give them in **Settings › Customer access**.

<Callout type="info">
  A drop-in chat component and an embeddable page are on the way. Until then, you build the chat on the API below.
  It streams the same answers the component will draw.
</Callout>

The chat embed runs on your Production environment.

## A token for each user

The browser talks to the assistant with a short-lived token for the signed-in user. Choose how your app gets one in
**Customer access**:

- **Your own JWT.** If Customer access is set to accept your app's JWTs (Clerk, Auth0, Supabase, Cognito or any JWKS
  issuer), the token your sign-in provider already gives the browser works as it is. Customer access reads the
  customer from its claim. There is nothing to add on your server.
- **A hypequery token minted by your backend.** Your server checks who is signed in, then swaps them for a token:

<CodeBlock>
```ts
// app/api/hypequery-token/route.ts: runs on your server, with your key.
export async function POST() {
  const user = await getSignedInUser(); // Your own auth.
  if (!user) return new Response(null, { status: 401 });

  const response = await fetch('https://<environment-slug>.hypequery.app/embed/tokens', {
    method: 'POST',
    headers: {
      Authorization: `Bearer ${process.env.HYPEQUERY_API_KEY}`,
      'Content-Type': 'application/json',
    },
    body: JSON.stringify({
      subject: user.id,
      tenantId: user.customerId, // Which customer's rows they see.
      permissionSet: '<permission set>', // Its name in Customer access.
    }),
  });
  // { token, expiresAt }: a token for this user only, valid for minutes.
  return Response.json(await response.json(), { status: response.status });
}
```
</CodeBlock>

Take `subject` and `tenantId` from your server-side session, never from the request. Mint a new token before
`expiresAt`. The API key stays on your server. The customer must be registered in the environment's tenant registry.

## Chat from the browser

Start a thread, then send each message to it. The assistant's turn streams back as NDJSON: one JSON object per line.

<CodeBlock>
```ts
// chat.ts
const ORIGIN = 'https://<environment-slug>.hypequery.app';
const token = (await (await fetch('/api/hypequery-token', { method: 'POST' })).json()).token;
const headers = { Authorization: `Bearer ${token}`, 'Content-Type': 'application/json' };

// One thread per conversation.
const { thread } = await (
  await fetch(`${ORIGIN}/embed/threads`, { method: 'POST', headers, body: '{}' })
).json();

export async function ask(text: string, onEvent: (event: ChatEvent) => void) {
  const response = await fetch(`${ORIGIN}/embed/threads/${thread.id}/messages`, {
    method: 'POST',
    headers,
    body: JSON.stringify({ text }),
  });
  // The turn streams as one JSON object per line.
  const reader = response.body!.pipeThrough(new TextDecoderStream()).getReader();
  let buffered = '';
  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;
    buffered += value;
    const lines = buffered.split('\n');
    buffered = lines.pop()!;
    for (const line of lines) if (line.trim()) onEvent(JSON.parse(line));
  }
}

type ChatEvent =
  | { type: 'activity'; label: string } // "Thinking", "Running a query"
  | { type: 'text'; delta: string } // The reply, a piece at a time.
  | { type: 'answer'; answerId: string; title: string; dataset: string; query: unknown; chart: unknown; rowCount: number }
  | { type: 'analysis'; action: 'created' | 'updated'; analysisId: string; title: string; revision: number }
  | { type: 'notice'; message: string }
  | { type: 'error'; message: string }
  | { type: 'done' };
```
</CodeBlock>

With your own JWT, set `token` to your sign-in provider's token for the user instead of calling the token route.

Your app's origin must be in the environment's allowed origins, under **Customer access**. Add
`http://localhost:3000` for development, or the browser's requests are refused.

### The events

| Event | What to do |
| --- | --- |
| `activity` | Show what the assistant is doing, such as "Thinking" or "Running a query". |
| `text` | Append `delta` to the reply as it streams. |
| `answer` | An answer card. Run its `query` against the `dataset`'s endpoint with the same token, and draw the `chart` it names. |
| `analysis` | The assistant created or updated one of the user's saved analyses. Reload it. |
| `notice` | A message to show the user, for example when a usage limit ended the turn early. |
| `error` | The turn failed. Show `message`. |
| `done` | The turn is complete and stored. |

Answers carry queries, not rows, so the numbers your app shows always come from running the query.

## Threads

| Request | Does |
| --- | --- |
| `GET /embed/threads` | Lists the user's threads, most recent first. |
| `POST /embed/threads` | Starts a thread. The body can set a `title`. |
| `GET /embed/threads/{id}` | Returns the thread's messages and answer cards. |
| `POST /embed/threads/{id}/messages` | Sends `{ "text" }` and streams the assistant's turn. |
| `DELETE /embed/threads/{id}` | Hides the thread. |

The server keeps the transcript: the browser sends only the new message. One turn runs per thread at a time; a second
message while a turn is running gets `409` with `HQ_CLOUD_THREAD_BUSY`. Threads expire 90 days after their last
activity.

## Usage limits

Messages and tokens are limited per user, per customer and per organisation. A request over a limit gets `429`, a
`Retry-After` header and the code `HQ_CLOUD_EMBED_USAGE_LIMIT`:

<CodeBlock>
```json
{ "error": { "code": "HQ_CLOUD_EMBED_USAGE_LIMIT", "message": "You've reached today's message limit. Try again tomorrow.", "limit": "user-messages" } }
```
</CodeBlock>

The `message` is written for your end user, so you can show it as it is. Set the per-customer limits in
**Customer access**.
