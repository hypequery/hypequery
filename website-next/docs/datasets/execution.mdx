import { CodeBlock } from 'fumadocs-ui/components/codeblock';


`createDatasetClient` is the execution surface for datasets and metrics. In a ClickHouse app, pass the same query builder instance you use for hand-written queries.

<CodeBlock>
```typescript
import { createDatasetClient } from '@hypequery/datasets';
import { createQueryBuilder } from '@hypequery/clickhouse';

const db = createQueryBuilder({
  url: process.env.CLICKHOUSE_URL!,
  username: process.env.CLICKHOUSE_USER!,
  password: process.env.CLICKHOUSE_PASSWORD!,
  database: process.env.CLICKHOUSE_DATABASE!,
});

const analytics = createDatasetClient({ queryBuilder: db });
```
</CodeBlock>

Use `db.table(...)` for local typed queries and `analytics.execute(...)` for semantic dataset or metric queries. Both paths share the same ClickHouse connection.

## Execution methods

The dataset client exposes these methods:

| Method | Use it for |
| --- | --- |
| `analytics.validate(target, query, context?)` | Check a query without generating or executing SQL |
| `analytics.toSQL(target, query, context?)` | Inspect generated SQL without executing it |
| `analytics.compileDataset(dataset, query, context?)` | Preview execution SQL, effective limits, dependencies, and preflight statements |
| `analytics.execute(target, query, context?)` | Validate, generate SQL, execute, and return rows |

The `target` can be a metric, a grained metric, or a dataset. `compileDataset` accepts datasets only and requires the query-builder execution path.

## Validate

Use `validate` when you want errors as data instead of exceptions.

<CodeBlock>
```typescript
const validation = analytics.validate(revenue, {
  dimensions: ['country'],
  filters: [eq('status', 'completed')],
});

if (!validation.valid) {
  console.error(validation.errors);
}
```
</CodeBlock>

Validation checks dimensions, measures, filters, order fields, limits, time grain requirements, tenant context, and derived metric plans.

## Generate SQL

Use `toSQL` to inspect the generated query.

<CodeBlock>
```typescript
const sql = analytics.toSQL(revenue, {
  dimensions: ['country'],
  filters: [eq('status', 'completed')],
  orderBy: [{ field: 'revenue', direction: 'desc' }],
  limit: 10,
});
```
</CodeBlock>

`toSQL` validates first. Invalid queries throw with the same validation errors that `execute` would throw.

## Preview dataset execution

`compileDataset` and dataset execution use the same compilation pipeline for base,
derived, window, and shift measures. Compilation does not execute a query. It
includes the dataset's effective result ceiling and the extra row fetched to
determine `pagination.hasMore`. Window and shift queries also expose their
time-axis guard query in `preflightStatements`.

<CodeBlock>
```typescript
const query = { measures: ['revenue'], limit: 10 } as const;
const compiled = analytics.compileDataset(Orders, query);

// Structural diagnostics omit SQL, physical columns, filter values and tenant IDs.
console.log(compiled.describe());
// JSON.stringify(compiled) produces the same structural description.

const result = await analytics.execute(Orders, query);
```
</CodeBlock>

Provide the same trusted tenant context and runtime builder override to compilation
and execution. Invalid definitions or queries fail during compilation. SQL and
parameters are available through `compiled.sql` and `compiled.parameters` for an
authorized debugger; custom query builders may inline values into SQL, so those
fields must not be returned as public diagnostics. The normalized `compiled.query`
also contains filter values. `toSQL` retains its logical query behavior, including
the requested limit; use `compileDataset` to preview the actual execution limit.

### UI and cross-language authoring

The UI can author a portable deployment definition directly. Validate it using
the protocol package, then load it with `rehydrateProtocolDeploymentContract`.
TypeScript and Python authors export the same deployment vocabulary. Cloud's
portable runtime rebuilds these definitions and uses the TS dataset compiler;
Python local execution uses its own native planner.

Providers can use `createPortableSemanticRuntime({ queryBuilder: db })` for both
`runtime.compile(input)` and `runtime.execute(input)`. Both resolve the same
activation catalog, tenant context, and row budget. These are trusted adapter
operations: the deployment data plane or an equivalent provider boundary must
authenticate and authorize the request before supplying the input. Compilation
does not run preflight guard statements; execution runs them before reading rows.
Portable compilation includes `activationRevision` in its structural description
so the diagnostic record identifies the definition generation used.

Use the shipped capability matrix to enable authoring controls for a target:

<CodeBlock>
```typescript
import { DATASET_EXECUTION_CAPABILITIES } from '@hypequery/datasets';

const cloudFeatures = DATASET_EXECUTION_CAPABILITIES.features
  .filter(feature => feature.cloud)
  .map(feature => feature.feature);
```
</CodeBlock>

The matrix distinguishes protocol representation, TS/Python local support,
TS/Python publication, and repository Cloud execution. It covers base and derived
measures, segments, window/shift measures, approximate distinct counts, and sub-day
grains. It is a conservative feature discovery aid, not per-definition validation
or a statement that a hosted service has qualified Python deployments.

Publishing currently emits deployment v2. Protocol v3 acceptance alone does not
enable v3 features in the portable runtime. When adding a portable dataset feature,
complete its protocol representation, SDK authoring/export, Cloud rehydration and
execution, and Python native planning; update the matrix and its TS/Python probes
together. Enable UI controls only for a target whose executable support is present.

## Execute a metric

Metric execution returns one named KPI, optionally grouped by dimensions or time.

<CodeBlock>
```typescript
const revenue = Orders.metric('revenue', { measure: 'revenue' });

const result = await analytics.execute(revenue, {
  dimensions: ['country'],
  filters: [eq('status', 'completed')],
  orderBy: [{ field: 'revenue', direction: 'desc' }],
  limit: 10,
});
```
</CodeBlock>

Use `by` for time bucketing. It is a flat grain value, not an object:

<CodeBlock>
```typescript
const result = await analytics.execute(revenue, {
  by: 'month',
  dimensions: ['country'],
});
```
</CodeBlock>

## Execute a dataset

Dataset execution returns an ad hoc selection of dimensions and measures from one dataset.

<CodeBlock>
```typescript
const result = await analytics.execute(Orders, {
  dimensions: ['country', 'status'],
  measures: ['revenue', 'orderCount'],
  filters: [eq('status', 'completed')],
  limit: 10,
});
```
</CodeBlock>

Dataset queries use the same `by` field when the dataset declares a `timeKey`:

<CodeBlock>
```typescript
const result = await analytics.execute(Orders, {
  by: 'day',
  dimensions: ['status'],
  measures: ['revenue', 'orderCount'],
});
```
</CodeBlock>

## Execution context

Pass execution context as the third argument. This is where runtime tenant scope and per-call builder overrides live.

<CodeBlock>
```typescript
await analytics.execute(revenue, {
  dimensions: ['country'],
}, {
  runtime: {
    tenant: 'tenant_123',
  },
});
```
</CodeBlock>

When a dataset has `tenantKey`, tenant context is required unless you explicitly use a trusted cross-tenant scope. Datasets auto-inject the tenant filter from `tenantKey`.

## Result metadata

`execute` returns rows plus metadata.

<CodeBlock>
```typescript
const result = await analytics.execute(revenue, {
  dimensions: ['country'],
  limit: 25,
});

result.data;
result.meta?.sql;
result.meta?.timingMs;
result.meta?.rowCount;
result.meta?.pagination;
```
</CodeBlock>

Pagination metadata is present when a query sets `limit`. Hypequery over-fetches one extra row to compute `hasMore` without issuing a separate count query.

<CodeBlock>
```typescript
{
  limit: 25,
  offset: 0,
  hasMore: true,
}
```
</CodeBlock>
