Filters are structured query objects. They are used by metric queries, dataset queries, and filtered measures.

<CodeBlock>
```typescript
import {
  between,
  eq,
  gt,
  gte,
  inList,
  like,
  lt,
  lte,
  neq,
  notInList,
} from '@hypequery/datasets';
```
</CodeBlock>

## Filter helpers

<CodeBlock>
```typescript
eq('status', 'completed')
neq('status', 'cancelled')
gt('amount', 100)
gte('amount', 100)
lt('amount', 1000)
lte('amount', 1000)
inList('country', ['US', 'UK', 'CA'])
notInList('status', ['cancelled', 'refunded'])
between('createdAt', '2026-01-01', '2026-01-31')
like('email', '%@example.com')
```
</CodeBlock>

Each helper returns a filter with a field, operator, and value.

<CodeBlock>
```typescript
eq('status', 'completed')
// { field: 'status', operator: 'eq', value: 'completed' }
```
</CodeBlock>

## Use filters in metric queries

<CodeBlock>
```typescript
await analytics.execute(revenue, {
  dimensions: ['country'],
  filters: [
    eq('status', 'completed'),
    gte('amount', 100),
    inList('country', ['US', 'UK', 'CA']),
  ],
});
```
</CodeBlock>

## Use filters in dataset queries

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  dimensions: ['country', 'status'],
  measures: ['revenue', 'orderCount'],
  filters: [
    eq('status', 'completed'),
    between('createdAt', '2026-01-01', '2026-01-31'),
  ],
});
```
</CodeBlock>

## Filter aggregated values with `having`

`filters` narrow the rows before they are aggregated. To keep only the groups whose aggregated value passes a condition, such as countries with more than 10,000 in revenue, use `having`:

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  dimensions: ['country'],
  measures: ['revenue', 'orderCount'],
  filters: [eq('status', 'completed')],
  having: [
    { measure: 'revenue', operator: 'gt', value: 10_000 },
    { measure: 'orderCount', operator: 'between', value: [2, 50] },
  ],
});
```
</CodeBlock>

- Each condition must name a measure the query selects, including derived measures. A condition on an unselected measure is rejected.
- Values are finite numbers, bound as query parameters. Operators are `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `between` (a `[min, max]` pair), `in` and `notIn` (non-empty arrays).
- Conditions apply after grouping and before ordering and limits. A group whose measure is `NULL` never matches.
- A dataset's `limits.maxFilters` bounds `filters` and `having` together.
- Queries that select window or shift measures do not accept `having`.

## Use filters in measures

Filtered measures are useful when a business state should always be part of the aggregation.

<CodeBlock>
```typescript
import { dataset, dimension, eq, measure } from '@hypequery/datasets';

const Orders = dataset('orders', {
  source: 'orders',
  dimensions: {
    status: dimension.string(),
  },
  measures: {
    completedRevenue: measure.sum('amount', {
      filters: [eq('status', 'completed')],
    }),
    refundedRevenue: measure.sum('amount', {
      filters: [eq('status', 'refunded')],
    }),
  },
});
```
</CodeBlock>

## Restrict filter operators

By default, filterable dimensions become available as filters. Use the dataset `filters` map when you want a named filter contract or a restricted operator set.

<CodeBlock>
```typescript
import { dataset, dimension, measure } from '@hypequery/datasets';

const Orders = dataset('orders', {
  source: 'orders',
  dimensions: {
    status: dimension.string(),
    country: dimension.string(),
  },
  measures: {
    revenue: measure.sum('amount'),
  },
  filters: {
    status: {
      __type: 'filter_definition',
      field: 'status',
      operators: ['eq', 'neq', 'in', 'notIn'],
    },
  },
});
```
</CodeBlock>

With this contract, `status` is the only exposed filter field, and only the listed operators are allowed. TypeScript checks these names and operators in dataset and metric execution, Serve API inputs, and React hooks, including infinite-query hooks. The filter helpers preserve their operator literals, so `eq('status', 'completed')` works with an `eq`-only policy.

Use `DatasetQueryFor<typeof Orders>` or `MetricQueryFor<typeof Orders, 'revenue'>` when storing query inputs in variables. `DatasetFilterNames<typeof Orders>` describes the exposed names, and `DatasetFilterFor<typeof Orders>` describes the field/operator pairs. A filter's name is the key in the allowlist, which may differ from its backing dimension.

Omitting `filters` generates an allowlist from dimensions with `filterable !== false`; an explicit empty map disables local filters. One-hop `belongsTo` and `hasOne` filters follow the target dataset's allowlist and operator policy. SQL-backed target dimensions, `hasMany`, and multi-hop paths remain unavailable.

Keep dataset definitions inferred to retain their literal policies. Broad `DatasetInstance` or `SemanticFiltersDefinition` annotations lose that information. Explicit result-row generic calls retain the legacy dynamic-query contract. Filter values and runtime tenant restrictions continue to be validated when the query runs.

## Order helpers

`asc` and `desc` create structured order clauses.

<CodeBlock>
```typescript
import { asc, desc } from '@hypequery/datasets';

await analytics.execute(revenue, {
  dimensions: ['country'],
  orderBy: [desc('revenue'), asc('country')],
});
```
</CodeBlock>

## Tenant filters

When runtime tenancy is active, explicit filters on the tenant field are rejected. Use runtime tenant context instead.

<CodeBlock>
```typescript
await analytics.execute(revenue, {
  filters: [eq('tenantId', 'tenant_123')],
}, {
  runtime: {
    tenant: 'tenant_123',
  },
});
// Error: Cannot filter on tenant field "tenantId" when runtime tenancy enforcement is active.
```
</CodeBlock>
