Measures are aggregations over fields in a dataset. Callers can request values such as revenue, order count, average order amount, minimum value, or maximum value. Measure and metric result columns are returned as `string | null`: every non-null aggregate is normalized to a string across ClickHouse result types and execution backends, while SQL `NULL` remains `null`. Convert numeric values at the application boundary when needed.

The object key is the semantic API name. The first argument is the backing field to aggregate. If that field is a dimension, hypequery uses the dimension mapping to resolve the ClickHouse column.

<CodeBlock>
```typescript
measures: {
  revenue: measure.sum('amount', {
    label: 'Revenue',
    description: 'Total order amount before refunds.',
  }),
  orderCount: measure.count('id'),
  uniqueCustomers: measure.countDistinct('customerId'),
  averageAmount: measure.avg('amount'),
  minAmount: measure.min('amount'),
  maxAmount: measure.max('amount'),
}
```
</CodeBlock>

## Derived measures

Use `measure.derived` in the same `measures` object to calculate a value from
base aggregations. Each `uses` entry maps a formula input alias to the name of
a base measure in this dataset. The formula is symbolic, not a SQL string.

<CodeBlock>
```typescript
import {
  dataset, dimension, divide, measure, nullIfZero,
} from '@hypequery/datasets';

const Orders = dataset('orders', {
  source: 'orders',
  dimensions: { country: dimension.string() },
  measures: {
    revenue: measure.sum('amount'),
    orderCount: measure.count('id'),
    averageOrderValue: measure.derived({
      uses: { revenue: 'revenue', orders: 'orderCount' },
      formula: ({ revenue, orders }) =>
        divide(revenue, nullIfZero(orders)),
      label: 'Average Order Value',
    }),
  },
});

await analytics.execute(Orders, {
  dimensions: ['country'],
  measures: ['averageOrderValue'],
  orderBy: [{ field: 'averageOrderValue', direction: 'desc' }],
});
```
</CodeBlock>

The dataset definition type-checks dependency names against its base-measure
keys: a typo, a measure from another dataset, or a derived measure used as an
input is rejected. Formula inputs are typed from the `uses` aliases. At
runtime, definition validation also checks references, aliases, and cycles.
The query aggregates `revenue` and `orderCount` first, computes
`averageOrderValue`, then orders the result; dependencies are not returned
unless explicitly selected. A zero order count produces `null`.

Derived measures are included in dataset contracts and survive deployment
rehydration. Existing standalone metrics remain available for local and
self-hosted use; for new dataset-owned calculations, prefer this API. See
[Metrics](/docs/datasets/metrics) for the older named-metric API.

With that definition, callers use the semantic measure names:

<CodeBlock>
```typescript
await analytics.execute(Orders, {
  dimensions: ['country'],
  measures: ['revenue', 'orderCount'],
});
```
</CodeBlock>

All declared measure kinds are available on the returned dataset's `measures`
registry, including `Orders.measures.averageOrderValue`. The older
`Orders.derivedMeasures` property remains as a deprecated compatibility alias.
Queries that omit `measures` still select only base aggregations; select derived
and window measures explicitly. Standalone `dataset.metric()` definitions can
only wrap base measures.

## Window measures

Declare time windows in the same `measures` object:

<CodeBlock>
```typescript
const Orders = dataset('orders', {
  source: 'orders',
  timeKey: 'createdAt',
  dimensions: { createdAt: dimension.timestamp() },
  measures: {
    revenue: measure.sum('amount'),
    trailingRevenue: measure.trailing('revenue', { amount: 7, unit: 'day' }),
    monthToDateRevenue: measure.toDate('revenue', 'month'),
    runningRevenue: measure.cumulative('revenue'),
  },
});

Orders.measures.runningRevenue; // The window definition, alongside revenue.
```
</CodeBlock>

Each window references a base measure on its dataset and requires `timeKey`.
`cumulative` supports only `sum`, `count`, `min`, and `max`. A derived formula
may reference a base or window measure, but cannot reference another derived
measure.

Execute windows with `createDatasetClient({ queryBuilder })`. Select a grain
and exactly one bounded filter on the dataset's time field:

<CodeBlock>
```typescript
import { createDatasetClient } from '@hypequery/datasets';

const client = createDatasetClient({ queryBuilder: db });
const result = await client.execute(Orders, {
  by: 'day',
  measures: ['revenue', 'trailingRevenue', 'monthToDateRevenue', 'runningRevenue'],
  filters: [
    { field: 'createdAt', operator: 'gte', value: '2026-01-01' },
    { field: 'createdAt', operator: 'lt', value: '2026-02-01' },
  ],
});
```
</CodeBlock>

Use ISO timestamps with `between`, or a lower (`gt`/`gte`) and upper
(`lt`/`lte`) bound. The range selects output buckets. Windows include earlier
rows and the entire current bucket, whose end is exclusive. Base measure
columns still respect the original time filter, including partial buckets.

Every bucket appears for each dimension combination found in the scanned rows.
Missing base values are `null`; counts are `'0'`. Trailing distinct counts and
averages reaggregate source rows across the entire window. Segments, tenant
scope, non-time query filters, and measure filters apply throughout lookback.

Trailing intervals must convert to whole query buckets: for example, one week
with `by: 'day'`, or one year with `by: 'month'`. Calendar months cannot convert
to days. To-date periods must be strictly coarser than the query grain and
contain whole buckets. A row may contribute to at most 1,000 buckets. The
output series must fit the query's result limit or the dataset ceiling.

Buckets follow the physical time column's timezone. Date-only and timezone-free
bounds use that timezone; explicit offsets represent instants. Catalogs and
agent projections expose window parameters and `requiresTimeRange: true`.
Window-dependent formulas are selectable through the same query API.

Cloud publishing still rejects window definitions until deployment contract 3
support is available. The deprecated semantic backend path does not execute
windows. There is no separate `windowMeasures` property on a dataset instance.

## Period comparisons

Declare a shifted base measure in the same registry, then use it directly or
in a derived formula:

<CodeBlock>
```typescript
import { createDatasetClient } from '@hypequery/datasets';

const Orders = dataset('orders', {
  source: 'orders',
  timeKey: 'createdAt',
  dimensions: { createdAt: dimension.timestamp() },
  measures: {
    revenue: measure.sum('amount'),
    priorYearRevenue: measure.shift('revenue', { amount: 1, unit: 'year' }),
    revenueGrowth: measure.derived({
      uses: { current: 'revenue', prior: 'priorYearRevenue' },
      formula: ({ current, prior }) =>
        divide(subtract(current, prior), nullIfZero(prior)),
    }),
  },
});

const client = createDatasetClient({ queryBuilder: db });
const result = await client.execute(Orders, {
  by: 'month',
  measures: ['revenue', 'priorYearRevenue', 'revenueGrowth'],
  filters: [
    { field: 'createdAt', operator: 'gte', value: '2026-01-01' },
    { field: 'createdAt', operator: 'lt', value: '2027-01-01' },
  ],
});
```
</CodeBlock>

At each bucket, a shift aggregates rows in
`[bucket start − interval, bucket end − interval)`. The interval must be a
positive safe integer and convert to whole query buckets under the window
conversion rules. For example, one year works with monthly, quarterly, or
yearly buckets; one month cannot shift daily or weekly buckets. Subtraction
uses calendar arithmetic, with ClickHouse's end-of-month clamping.

Shifted measures require a grain and one bounded time range, and use the same
filled series as windows. The range selects output buckets; shifted values use
the entire earlier bucket even when the output range includes partial buckets.
Tenant scope, segments, non-time query filters, and the wrapped measure's
filters apply to those earlier rows. Missing shifted counts are `'0'`; other
missing values are `null`. Derived formulas can combine base, window, and
shifted measures.

Date and timestamp buckets use the physical time column's timezone. Across
DST, shifted endpoints can cover a different number of source hours; values
still follow the exact half-open range. Ordering and pagination happen after
comparisons and formulas. Minute and hour grains require a time-of-day column;
physical `Date` and `Date32` columns are rejected during metadata validation.
Catalogs expose `kind: 'shift'`, the base measure,
the interval, and `requiresTimeRange: true`.

Shifts can wrap only base measures on their dataset. They cannot wrap a
window, another shift, or a derived measure, and cannot be selected through a
relationship or a standalone metric. Cloud publishing requires the separate
deployment contract 3 implementation; the deprecated backend path does not
execute shifts.

## Aggregation helpers

- `measure.shift(baseMeasure, interval, opts?)`
- `measure.sum(field, opts?)`
- `measure.count(field, opts?)`
- `measure.countDistinct(field, opts?)`
- `measure.approxCountDistinct(field, opts?)`
- `measure.avg(field, opts?)`
- `measure.min(field, opts?)`
- `measure.max(field, opts?)`
- `measure.percentile(field, level, opts?)`
- `measure.median(field, opts?)`
- `measure.argMax(field, by, opts?)`
- `measure.argMin(field, by, opts?)`
- `measure.stddev(field, opts?)`
- `measure.variance(field, opts?)`

The helper determines the aggregation. The field should be the semantic field name when it exists in `dimensions`, or the physical column name when you are aggregating a raw table column.

`percentile` uses ClickHouse's approximate `quantile(level)` aggregation, where
`level` is between `0` and `1`. `median` is shorthand for `percentile(field,
0.5)`. `stddev` and `variance` use sample statistics (`stddevSamp` and
`varSamp`).

`approxCountDistinct` estimates the number of distinct values with ClickHouse
`uniq`. It uses bounded memory, so it stays fast on high-cardinality columns such
as user or session IDs. Use `countDistinct` when the number has to be exact.
Catalogs, the semantic contract and the agent-safe catalog mark these measures,
and any derived measure that uses one, with `approximate: true`. That lets
agents and UIs present the value as an estimate. Hypequery Cloud cannot publish
approximate measures yet: they need deployment contract 3 (RFC 0015), so
publishing refuses them with an error naming the measure.

`argMax` and `argMin` return the value of `field` from the row where `by` is
greatest or smallest. The `by` field can use a semantic dimension name, so
column mappings are respected:

<CodeBlock>
```typescript
measures: {
  p95Latency: measure.percentile('latencyMs', 0.95),
  medianLatency: measure.median('latencyMs'),
  latestStatus: measure.argMax('status', 'createdAt'),
  firstStatus: measure.argMin('status', 'createdAt'),
  latencyStddev: measure.stddev('latencyMs'),
  latencyVariance: measure.variance('latencyMs'),
}
```
</CodeBlock>

The percentile, standard deviation, and variance helpers support measure-local
filters. Filters are intentionally not supported on `argMax` or `argMin`
because NULL handling for conditional arg aggregates differs across ClickHouse
versions. Use a query-level filter when filtering an arg aggregate.

## Options

Most measure helpers accept the following options object. `argMax` and `argMin`
accept `sql`, `label`, and `description`, but not `filters`.

<CodeBlock>
```typescript
type MeasureOptions = {
  sql?: string;
  label?: string;
  description?: string;
  filters?: MetricFilter[];
};
```
</CodeBlock>

| Option | Use it for |
| --- | --- |
| `sql` | Aggregating a SQL expression instead of a simple field |
| `label` | Human-readable display text for docs, UIs, metrics, and agents |
| `description` | Longer metadata for generated docs, UIs, metrics, and agents |
| `filters` | Applying measure-local filters before the aggregation is computed |

## Field mapping

Measures reference fields by name. When the field is a dimension with a `column` mapping, the measure follows that mapping.

<CodeBlock>
```typescript
dimensions: {
  customerId: dimension.string({ column: 'customer_id' }),
  amount: dimension.number(),
},
measures: {
  uniqueCustomers: measure.countDistinct('customerId'),
  revenue: measure.sum('amount'),
}
```
</CodeBlock>

In this example, callers use `uniqueCustomers`, and the generated SQL counts distinct `customer_id`.

## Labels and descriptions

Use `label` and `description` for human-readable metadata. These do not change SQL generation.

<CodeBlock>
```typescript
measures: {
  revenue: measure.sum('amount', {
    label: 'Revenue',
    description: 'Total order amount before refunds.',
  }),
}
```
</CodeBlock>

When you promote a measure into a base metric, the metric inherits the measure label and description unless you override them on the metric.

<CodeBlock>
```typescript
const revenue = Orders.metric('revenue', { measure: 'revenue' });
```
</CodeBlock>

For MCP, measures are exposed through `get_dataset_schema` for ad hoc dataset queries. When you promote a measure into a named metric, the metric can inherit the measure label and description for agent-facing KPI queries.

## SQL-backed measures

Use `sql` when the aggregation should operate on an expression rather than a simple field.

<CodeBlock>
```typescript
measures: {
  taxedRevenue: measure.sum('amount', {
    sql: 'amount * 1.2',
  }),
}
```
</CodeBlock>

The `field` argument still names the logical backing field, while `sql` provides the expression to aggregate. Use SQL-backed measures sparingly. Schema compatibility checks can inspect simple fields, but complex SQL expressions can only produce warnings because they cannot be fully verified from the table schema.

SQL-backed measures require builder-backed execution. Generic semantic backend plans reject SQL-backed measures because cross-backend adapters cannot assume the same SQL expression syntax.

<Callout type="warn" title="Trusted model code">
  The `sql` option is authored in your dataset definition. Runtime callers should only request the semantic measure name, not provide SQL. See [Trust Boundaries](/docs/reference/trust-boundaries).
</Callout>

## Filtered measures

Use filtered measures for common business states instead of repeating the same filters in every query.

<CodeBlock>
```typescript
import { dataset, dimension, eq, measure } from '@hypequery/datasets';

const Orders = dataset('orders', {
  source: 'orders',
  dimensions: {
    status: dimension.string(),
  },
  measures: {
    completedRevenue: measure.sum('amount', {
      filters: [eq('status', 'completed')],
    }),
    refundedRevenue: measure.sum('amount', {
      filters: [eq('status', 'refunded')],
    }),
  },
});
```
</CodeBlock>
