The CLI provides telemetry preferences and a staged telemetry core. Normal runs
do not collect or send events yet. To audit locally, set
`HYPEQUERY_TELEMETRY_DEBUG=1`: valid event envelopes are printed to stderr and
nothing is sent. Maintainers can set `HYPEQUERY_TELEMETRY_URL` to a staging or
self-hosted first-party ingest endpoint. Opt-outs apply in both modes.

```bash
hypequery telemetry status
hypequery telemetry disable
hypequery telemetry enable
```

`status` (also the default action) prints the effective preference, the setting
that determined it, and a random install ID. Saving `enable` does not override
environment variables or the global flag.

To disable for one invocation, pass `--no-telemetry` before or after the command,
or set `DO_NOT_TRACK=1` or `HYPEQUERY_TELEMETRY_DISABLED=1`. These take precedence
over saved preferences. Test environments and Hypequery's own CI also disable
telemetry; customer CI follows the saved preference, which defaults to enabled.

Settings are stored in `telemetry.json` in the CLI config directory. They contain
the preference, a random install ID, a schema version, and an optional notice
timestamp reserved for the first-run notice. The install ID is generated randomly,
not from hardware, a username, or a hostname. Corrupt or unavailable settings
disable telemetry for that run. A failed explicit save reports an error so you
can use an environment variable or the flag instead.

See the [CLI reference](/docs/reference/api/cli#hypequery-telemetry) for precedence
and config-directory details. The planned event reference is below;
data-handling policy will be documented before default collection is released.

## Staging and debugging

```bash
HYPEQUERY_TELEMETRY_DEBUG=1 hypequery --version
HYPEQUERY_TELEMETRY_DEBUG=1 hypequery init --no-telemetry # Prints no events
```

Debug output contains the exact validated event envelopes, including their
timestamps and the transport-owned `$process_person_profile: false` and
`$geoip_disable: true` properties. Invalid events are dropped with a fixed
diagnostic that does not echo rejected input. All telemetry output uses stderr.

Staging delivery uses one in-memory batch per invocation, a built-in Node
HTTP(S) request, a 40 ms flush timeout, and a 64 KiB / 32-event cap. Unsent events are dropped;
there is no retry process or disk queue. Only HTTPS endpoints and HTTP loopback
test endpoints are accepted; URLs with credentials, query strings or fragments
are rejected, and redirects are refused. The first-party proxy holds the real
PostHog API key and must remove client IP information before forwarding.

HTTP 410 from the proxy disables the current CLI version in local settings,
best-effort. Later versions remain eligible; `telemetry status` reports
`kill_switch` when it applies. A read-only config cannot persist the response.

The disclosure appears once on enabled interactive runs, after a successful
stderr write. It is suppressed in CI, on non-TTY streams, during preference
commands, and under MCP. Before default collection is enabled, this disclosure
appears only when the staged core is activated as described above.

Known command failures reach the bounded exit flush. Dev shutdown flushes after
runtime teardown, and SIGINT/SIGTERM endings are classified as interrupted.
Crash events use Node's exception monitor so native fatal-error output and exit
behavior are preserved; network delivery during a fatal crash is best-effort.

In staged mode, `init` adds onboarding progress to its single command completion
event: the furthest stage reached, the failing stage on errors, connection results,
scaffold and authentication choices, bucketed schema/dataset counts, and whether
configuration files were created, updated, unchanged, or skipped. Declining setup
is recorded as cancellation. Connection retries share the same invocation and
produce one completion event. Table selections are recorded only as a selection
mode; table names, connection details, and output paths are never included.

## Event reference

Schema version: **1**. Default collection is inactive. The staged core emits command/crash lifecycle events in debug or explicitly configured ingest mode; init includes onboarding metrics. Other command-specific, session and project-feature instrumentation follows separately.

Unknown events, properties, record keys, flag names, enum values, and malformed identities or versions are rejected. No argument values, paths, names, SQL, messages, stacks, hosts, tenants, or credentials are permitted.

Counts use inclusive integer ranges: 0, 1, 2–5, 6–20, 21–100, and 101 or more. Duration and nonzero size buckets include their lower bound and exclude their upper bound. Raw counts, durations, ports and byte sizes are never sent.

MCP client identity/version is excluded from v1 pending the privacy decision. Auth strategies are recorded only as none/configured/unknown, since user-supplied functions have no safe built-in type identifier.

Cache scopes are classified only as unscoped/tenant/explicit/unknown from configuration presence. Explicit scopes are user content and are never read into a payload.

Project IDs follow HQ-233: the CLI uses the shared global salt, then the ingest proxy re-keys the digest with a server-side HMAC secret before storage. A hash is a pseudonymous project signal, not proof of anonymity. Cloud accounts are never linked to install IDs.
